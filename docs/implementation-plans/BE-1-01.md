```
│   ├── application/
│   │   └── game.service.ts              # use-case orchestration (the inbound port)
│   ├── ports/
│   │   └── game-repository.port.ts      # outbound port (interface + Symbol)
│   ├── adapters/
│   │   ├── api/
│   │   │   ├── game.controller.ts       # driving adapter (REST)
│   │   │   └── game.response.dto.ts     # response DTO
│   │   └── persistence/
│   │       └── prisma-game.repository.ts  # driven adapter (stub until DB-schema issue)
│   ├── game.mapper.ts                   # domain <-> persistence mapping
│   └── game.module.ts                   # DI wiring
├── app.module.ts
└── main.ts
```

**Rationale for each directory:**

- `domain/model/` — Pure domain entities. Zero framework imports. This is the innermost ring.
- `ports/` — Outbound port interfaces + Symbol tokens. These are the contracts the application layer depends on. Placed at the module level (not nested inside domain or application) because both layers reference them. Sairyss keeps ports in `database/` or `libs/`, Kaddir keeps them in `domain/ports/`. Placing them in a top-level `ports/` directory within the module is a clean middle ground.
- `application/` — Use-case services that orchestrate domain logic and call outbound ports. This is the layer that Sairyss calls "Application Services" and Kaddir calls the "Input Port."
- `adapters/api/` — Driving adapters (controllers, DTOs). Kaddir's `adapters/api/` pattern.
- `adapters/persistence/` — Driven adapters (repository implementations). Kaddir's `adapters/db/` pattern, renamed for clarity since we're using Prisma, not raw DB access.
- `game.mapper.ts` — At the module root, shared by any adapter that needs to convert to/from domain objects.

#### 2.2 [NEW] Domain model — `game/domain/model/game.ts`

Pure TypeScript. No `@nestjs/*` imports, no `@prisma/*` imports. Contains business logic and invariant enforcement.

```typescript
export type GameStatus = 'WAITING' | 'IN_PROGRESS' | 'FINISHED';

export class Game {
  constructor(
    public readonly id: string,
    public status: GameStatus,
    public readonly createdAt: Date,
    public updatedAt: Date,
  ) {}

  start(): void {
    if (this.status !== 'WAITING') {
      throw new Error(`Cannot start game in status "${this.status}"`);
    }
    this.status = 'IN_PROGRESS';
    this.updatedAt = new Date();
  }

  finish(): void {
    if (this.status !== 'IN_PROGRESS') {
      throw new Error(`Cannot finish game in status "${this.status}"`);
    }
    this.status = 'FINISHED';
    this.updatedAt = new Date();
  }
}
```

The domain model owns state transitions and guards invariants. Nothing in this file knows about HTTP, databases, or NestJS.

#### 2.3 [NEW] Outbound port — `game/ports/game-repository.port.ts`

Interface + Symbol pattern, following Kaddir's approach:

```typescript
import { Game } from '../domain/model/game';

export interface GameRepositoryPort {
  save(game: Game): Promise<Game>;
  findById(id: string): Promise<Game | null>;
}

// Symbol serves as the DI token at runtime.
// The interface above provides compile-time type safety.
// Both are exported under the same name — TypeScript resolves
// the correct one based on usage context (type position vs value position).
export const GameRepositoryPort = Symbol('GameRepositoryPort');
```

This is the "dual export" pattern from Kaddir's article. When you write `@Inject(GameRepositoryPort)`, TypeScript resolves `GameRepositoryPort` as the Symbol (value position). When you write `private readonly repo: GameRepositoryPort`, TypeScript resolves it as the interface (type position). Same name, two different things, zero ambiguity.

#### 2.4 [NEW] Application service — `game/application/game.service.ts`

Implements use-case logic. Depends on the outbound port interface, never on the concrete adapter.

```typescript
import { Inject, Injectable } from '@nestjs/common';
import { Game } from '../domain/model/game';
import { GameRepositoryPort } from '../ports/game-repository.port';
import { randomUUID } from 'crypto';

@Injectable()
export class GameService {
  constructor(
    @Inject(GameRepositoryPort)
    private readonly gameRepository: GameRepositoryPort,
  ) {}

  async createGame(): Promise<Game> {
    const now = new Date();
    const game = new Game(randomUUID(), 'WAITING', now, now);
    return this.gameRepository.save(game);
  }

  async findGameById(id: string): Promise<Game | null> {
    return this.gameRepository.findById(id);
  }
}
```

Note the `@Inject(GameRepositoryPort)` — this is required because the type annotation `GameRepositoryPort` is an interface (erased at runtime). The decorator tells NestJS which Symbol token to resolve. This is the one extra line compared to the abstract-class approach, but it's standard NestJS practice and both sources use it.

The service class itself acts as the inbound port. The controller depends on it directly. No separate `PlayTurnUseCase` interface.

#### 2.5 [NEW] Response DTO — `game/adapters/api/game.response.dto.ts`

Controllers should never return raw domain entities. The DTO defines the public API contract:

```typescript
import { Game } from '../../domain/model/game';

export class GameResponseDto {
  readonly id: string;
  readonly status: string;
  readonly createdAt: string;
  readonly updatedAt: string;

  constructor(game: Game) {
    this.id = game.id;
    this.status = game.status;
    this.createdAt = game.createdAt.toISOString();
    this.updatedAt = game.updatedAt.toISOString();
  }

  static fromDomain(game: Game): GameResponseDto {
    return new GameResponseDto(game);
  }
}
```

Dates are serialized to ISO strings. If a domain field is renamed or restructured later, only this DTO changes — the API contract stays stable.

#### 2.6 [NEW] Driving adapter — `game/adapters/api/game.controller.ts`

Depends on `GameService` (inbound port) and uses the response DTO to shape output:

```typescript
import {
  Controller,
  Get,
  Post,
  Param,
  NotFoundException,
} from '@nestjs/common';
import { GameService } from '../../application/game.service';
import { GameResponseDto } from './game.response.dto';

@Controller('games')
export class GameController {
  constructor(private readonly gameService: GameService) {}

  @Post()
  async create(): Promise<GameResponseDto> {
    const game = await this.gameService.createGame();
    return GameResponseDto.fromDomain(game);
  }

  @Get(':id')
  async findOne(@Param('id') id: string): Promise<GameResponseDto> {
    const game = await this.gameService.findGameById(id);
    if (!game) {
      throw new NotFoundException(`Game ${id} not found`);
    }
    return GameResponseDto.fromDomain(game);
  }
}
```

The controller imports from `application/` (the service) and from its own `api/` directory (the DTO). It never touches `ports/` or `domain/` directly except through the service. `NotFoundException` is an HTTP concern — it belongs here in the adapter, not in the service.

#### 2.7 [NEW] Mapper — `game/game.mapper.ts`

Handles conversion between the domain `Game` entity and any persistence representation. For the skeleton, the persistence side uses a plain object type. When the Prisma schema is added, this will map to/from the generated Prisma type.

```typescript
import { Game, GameStatus } from './domain/model/game';

// Placeholder type until Prisma model is generated.
// Will be replaced with `import { Game as GameRecord } from '@prisma/client'`
export interface GamePersistenceModel {
  id: string;
  status: string;
  createdAt: Date;
  updatedAt: Date;
}

export class GameMapper {
  static toDomain(record: GamePersistenceModel): Game {
    return new Game(
      record.id,
      record.status as GameStatus,
      record.createdAt,
      record.updatedAt,
    );
  }

  static toPersistence(game: Game): GamePersistenceModel {
    return {
      id: game.id,
      status: game.status,
      createdAt: game.createdAt,
      updatedAt: game.updatedAt,
    };
  }
}
```

Static methods keep it simple. No need to make this injectable — it's pure data transformation with no dependencies.

#### 2.9 [NEW] Module wiring — `game/game.module.ts`

Binds the Symbol token to the concrete adapter, following Kaddir's module pattern:

```typescript
import { Module } from '@nestjs/common';
import { GameController } from './adapters/api/game.controller';
import { GameService } from './application/game.service';
import { PrismaGameRepository } from './adapters/persistence/prisma-game.repository';
import { GameRepositoryPort } from './ports/game-repository.port';

@Module({
  controllers: [GameController],
  providers: [
    GameService,
    {
      provide: GameRepositoryPort,  // ← the Symbol token
      useClass: PrismaGameRepository,
    },
  ],
  exports: [GameService],
})
export class GameModule {}
```

`GameService` is registered as a plain provider (NestJS resolves it by class reference). `GameRepositoryPort` uses `provide/useClass` to bind the Symbol to the concrete implementation.

To swap persistence implementations later (e.g., an in-memory adapter for testing), you change one line: `useClass: InMemoryGameRepository`. The service, controller, and domain are untouched. This is the core benefit both articles emphasize.

### Step 4 — Verify hex-arch dependency direction

Manual check. Confirm these five rules hold:

1. `domain/model/game.ts` imports **nothing** from `@nestjs/*`, `@prisma/*`, or any adapter/port directory.
2. `ports/game-repository.port.ts` imports only from `domain/`.
3. `application/game.service.ts` imports from `ports/` and `domain/` — never from `adapters/`.
4. `adapters/api/game.controller.ts` imports from `application/` and its own `api/` directory — never from `ports/` or `adapters/persistence/`.
5. `adapters/persistence/prisma-game.repository.ts` imports from `ports/`, `domain/` (via mapper), and `prisma.service` — never from `application/` or `adapters/api/`.

If all five hold, the dependency rule is intact. A `dependency-cruiser` config to enforce this automatically is a good backlog item for later.
